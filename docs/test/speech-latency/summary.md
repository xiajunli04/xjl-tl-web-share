## 2. 结论（可用于论文“发现问题 → 改进 → 验证”）

1. **问题定位**：用户感知的“慢”主要来自链路里的串行等待与整段缓冲，而非模型本身。主要包括：
   - 前端 MP3 要整句缓冲；
   - AI 回复整条共用一个音频 track；
   - 服务端扣住最后一包；
   - 合成要等译文全文；
   - 朗读接口三层整段缓冲。
2. **改进**：
   - 分段音频协议（seg / segLast / 终止包），分包即时下发；
   - 前端 MediaSource 渐进播放，不支持时按段降级；
   - 译文与回复边生成边切段合成，2 路预取；
   - 字幕逐句并行、不阻塞语音；
   - 朗读接口全链路流式；
   - 句末识别让路（尾部静音时不发起 partial）；
   - 新增可选的响应速度档位与实时语音模型引擎。
3. **验证**：
   - AI 对话首个可播放音频下降 50%（级联），实时语音模型下降 92%，均达到目标；
   - 同传短句 P90 下降 15%，P50 只下降 4–8%，**未达到 −15% 的目标**。原因是短句的剩余耗时主要是外部固定项：模型首字约 1.5 s、Edge 首包约 0.9 s、识别约 0.7 s。对比实验表明，直连百炼反而更慢，属于网络和供应商层面的问题，需要“说完即出声”时可选千问 S2S 引擎。
4. **质量不受影响**：同传识别错误率 4.5%、chrF 61.5–62.2、术语准确率 100%，与改造前一致；全部测试通过：
   - Python 598；
   - Spring 300；
   - 前端 333。
