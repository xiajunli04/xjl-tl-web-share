# 译桥 · LinguaBridge — 总体设计

> 本文档汇总 explore 阶段（2026-10-02）的调研结论与架构决策，是后续所有 OpenSpec change 的依据。
> 题目原文见 [信息.txt](信息.txt)。

---

## 1. 目标与定位

题目要求的模块：用户管理、翻译任务管理、多语言识别、Agent 任务编排、上下文翻译、术语辅助、历史记录、基础管理；
另需规范接口与异常处理、完成功能测试与性能验证。

**平台定位**：不是"套壳调用大模型"，而是一个 **执行过程可观测、效果可评估** 的翻译 Agent 平台。
Agent 相对单次 LLM 调用的增量能力：

| 能力 | 平台中的体现 | 参考来源 |
|---|---|---|
| 理解与规划 | analyze/plan 节点按语种、领域、长度选择执行路径 | — |
| 工具调用 | 语种识别、术语检索、翻译记忆检索作为工具 | — |
| 反思修正 | review → refine 循环（准确/流畅/风格/术语） | 吴恩达 translation-agent |
| 多级记忆 | 篇章摘要 + 专名表 + 短期窗口 | DelTA (ICLR 2025) |
| 人机协同 | 术语确认、歧义追问（LangGraph interrupt） | Lara Translate |

形态选择：**带规划节点的工作流图（LangGraph）**，而非自由对话式多 Agent——可控、可复现、成本可预期、便于测试与论文论证。

## 3. 总体架构

```
┌──────────────────────────────────────────────────────────────────────┐
│ web (Next.js)                                                        │
│ 翻译工作台 │ 同声传译 │ 图片翻译 │ 文档工作台 │ 术语库 │ 历史 │ 管理后台     │
└────────────────┬───────────────────────────────┬─────────────────────┘
                 │ REST + SSE (Bearer JWT)        │ WebSocket /ws/interpret（一次性票据，PCM16 上行 / JSON 事件下行）
┌────────────────▼─────────────────────────────────────────────────────┐
│ springboot-backend   业务中枢 / 数据主权                               │
│ 认证RBAC │ 任务+状态机 │ 术语库 │ 历史 │ 模型配置 │ 限流审计 │ Result<T>   │
│ 同传会话/会议室路由/转写落库 │ 图片存储与记录 │ 语音与解读代理                 │
└───────┬─────────────────────────────┬──────────────┬─────────────────┘
        │ 同步: HTTP + SSE (短文本/图片) │ 异步: Redis Stream (长文档) │ WS: 发言流
┌───────▼─────────────────────────────▼────────────────────────────────┐
│ python-backend (FastAPI + LangGraph)   智能能力层                     │
│ Agent编排图 │ 语种识别 │ 术语匹配 │ TM检索 │ 质量评审 │ LLM适配层        │
│ 同传引擎（级联 / 百炼 / 豆包 / Gemini / OpenAI）│ VAD·ASR·TTS │ 视觉 OCR    │
└───────┬───────────────────────┬──────────────────┬───────────────────┘
        ▼                       ▼                  ▼
  PostgreSQL 17+pgvector     Redis 7          LLM（OpenAI兼容 / Anthropic）、实时同传与图片翻译 API
  biz schema / ai schema
```

### 3.1 服务边界决策

| 决策 | 内容 | 理由 |
|---|---|---|
| 数据主权 | Spring 是 biz schema 唯一写入方 | 业务一致性、审计集中 |
| Python 数据访问 | 只读 biz 中术语表、模型配置；读写 ai schema | Agent 工具调用真实可用；向量检索在 Python 侧最自然 |
| DDL 来源 | Spring 侧 Flyway 统一管理全部业务表；LangGraph checkpoint 表由 setup() 自建 | "数据库脚本"交付物单一来源 |
| 对外入口 | 浏览器只访问 Spring；Python 不对外暴露，内部用 X-Internal-Token | 安全边界清晰 |
| 模型密钥 | 管理员后台录入，AES-GCM 加密入库，Python 用共享密钥解密 | 可运营 + 安全 |

## 4. Agent 编排

### 4.1 短文本图（同步 + SSE）

```
START → analyze(语种/领域/长度) → plan(选路径)
          ├─ fast:     translate ───────────────────────────┐
          └─ standard: retrieve(术语+TM) → translate → review ┤
                                     ▲          不通过(≤2轮)  │
                                     └──── refine ◀──────────┤
                                                    通过      ▼
                                    finalize(术语遵循校验·轨迹落库) → END
```

### 4.2 篇章图（异步任务）

| 阶段 | 内容 |
|---|---|
| P0 解析 | 原文 → 结构树（标题/段落/列表/代码块/表格），标记不翻译内容（代码、URL、占位符） |
| P1 全文分析 | 语种、领域、文体、全文摘要、候选术语/专名抽取 |
| P2 术语对齐 | 候选 ∩ 用户术语库 → 采用已有译法；新术语 LLM 建议译法（遵循领域惯例，拿不准时保留原文）；⏸ interrupt 用户确认（默认开启）→ 本任务术语表 |
| P3 结构化分块 | 按标题/段落边界，每块约 1500–3000 tokens，不跨标题、不拆段落 |
| P4 逐块翻译 | 上下文包翻译 → 规则术语检查（仅硬约束）→ 可选 LLM 评审（独立评审模型，按 MQM 严重度决定）→ refine(≤1) → 增量更新专名表 → 写 checkpoint |
| P5 一致性检查 | 同一源术语多译法检测与统一 |
| P6 组装输出 | 按原结构还原 Markdown，双语对照，导出 |
| P7 后编辑 | 用户在工作台修改 → 确认段落写入翻译记忆 |

分块执行策略（可配置，亦为实验变量）：串行（带前块上下文）/ 并行（仅依赖全局记忆）/ 混合（章间并行、章内串行，默认）。

**术语约束强度**（⑥ 根据消融实验发现的"术语锁定"引入）：术语库命中与用户确认（含修改、新增）的术语为**硬约束**——提示词中必须使用、参与规则检查与修正触发、一致性检查以其为准；未开启人工确认时自动采用的抽取术语为**软约束**——提示词中作为可按领域惯例调整的参考译法，不参与规则检查，一致性检查按多数决定。

**评审**（⑥）：管理员可指定一个独立的评审模型（全局唯一），评审调用使用它、修正仍由译者模型完成；是否修正由 MQM 严重度决定（存在 critical/major、硬约束术语未遵循或总分低于兜底分 75），短文本与文档共用这一规则。文档默认不评审（实验显示同模型自评几乎不触发修正却增加约 70% token），作为「质量优先」选项按需开启。

**断点续译**：LangGraph Postgres checkpointer，`thread_id = task_id`；worker 重启后从最后完成块继续；支持单段重试。

### 4.3 TranslationContext 上下文包

```
TranslationContext {
  terms:       [{source, target, note}]     术语库命中
  tm_examples: [{source, target, score}]    翻译记忆 top-k（few-shot），低于阈值丢弃
  domain_hint: string                       领域
  style:       faithful | fluent | creative 风格
  doc_memory:  {summary, proper_nouns}      篇章记忆
  session_ctx: [{role, source, target}]     会话上下文
}
```

LLM 适配层负责映射：Qwen-MT → 原生 translation_options；通用 LLM → 拼装 prompt。

**实际实现（④）**：
- `tm_examples`：用户级翻译记忆（`ai.translation_memory`，本地 `paraphrase-multilingual-MiniLM-L12-v2` 384 维向量 + pg_trgm）两路召回，按字符级模糊匹配度与语义相似度入选（短文本 fuzzy ≥ 0.6 或 semantic ≥ 0.65，取前 3 条；文档按段取最佳 1 条，0.7 / 0.75，全块最多 8 条），作为"参考译法与风格"而非强制译法写入提示词。记忆来源：工作台「存入记忆」、文档段落后编辑、已完成任务一键写入
- `session_ctx`：最近 6 轮已采用的原文与译文 + 早期摘要 + 会话专名表，由 Spring 组装后随请求下发，Python 无状态计算；在所有路径（含快速路径与修订）都注入

### 4.4 上下文策略：篇章为主、会话为辅

| 维度 | 篇章上下文（主） | 会话上下文（辅） |
|---|---|---|
| 可见性 | 全文可见，可预分析 | 只能看过去 |
| 主要问题 | 术语/专名/风格一致、结构保持 | 指代、省略、称谓、语气 |
| 时延 | 异步分钟级 | 实时 |
| 反思循环 | 完整 review/refine | 以快速路径为主；允许追问的会话走标准路径 |
| 记忆 | 全文摘要 + 专名表 + 前块 + 滚动摘要 | 最近 N 轮 + 早期摘要 + 实体表 |

共用 **ContextMemory 抽象**（短期窗口 + 长期摘要 + 实体表），按场景采用不同构建/更新策略。

会话上下文范围：
- **B（必做，④ 已实现）**：用户 ↔ Agent 迭代修订（revise 路径，版本链可切换采用版本）+ 歧义主动追问（plan 节点在判定领域的同一次调用中检查歧义，`interrupt` + AsyncPostgresSaver 检查点，`thread_id = turn:{requestId}`，回答后 `Command(resume)` 从断点继续）
- **A（可选，未做）**：双人跨语言对话模拟（跨境电商客服场景）

会话记忆的更新策略（与篇章滚动摘要同构）：已完成轮数超过窗口且距上次压缩新增 ≥ 3 轮时，finalize 之后由 memorize 节点用一次 LLM 调用把滑出窗口的轮次并入摘要、更新实体表，通过 `memory` 事件交 Spring 写回会话。实验效果见实验报告第 10 节。⑧.4 起，窗口改为"尚未并入摘要的最近轮次"（6–8 轮）：滑出窗口但还没压缩的轮次仍以原文出现，不再有"隐形"轮次。

**语音对话的记忆（⑧.4）**：同一套"短期窗口 + 长期摘要"思路延伸到实时语音场景。

| 场景 | 短期窗口 | 长期记忆 | 断线重建 |
|---|---|---|---|
| AI 对话（Lumi） | 尚未并入摘要的对话原文（16 轮时压缩最早 4 轮，最多 24 轮） | 滚动摘要（≤ 400 字，四节：用户信息 / 话题与要点 / 用户的问题 / 待办与约定），后台一次 LLM 调用生成；消息只在摘要提交后才移出窗口，没有缺口 | Spring 暂存成员最近 24 句定稿语句与最新摘要，重建发言流时经 config 的 `history` / `chat.memory` 下发，Python 恢复后不再重复开场白 |
| 同传（收听 / 对话 / 会议室） | 发言流级最近 6 句（≤ 1500 字符），双向对话含双方的原话与已有译文 | 不做摘要（口译的指代主要在相邻几句，专名一致靠术语库） | 同上，恢复最近语句 |

## 5. 调用模式与任务状态机

```
同步(短文本):  浏览器 ─SSE─▶ Spring ─SSE─▶ Python      推送 agent 节点事件 + token（事件体统一 JSON 包装）
异步(长文档):  浏览器 ─▶ Spring 建任务 ─▶ Redis Stream ─▶ Python worker
                         ▲                                    │
                         └──── 进度 (Redis Pub/Sub) ◀──────────┘

PENDING → ANALYZING → [AWAITING_CONFIRM] → TRANSLATING → REVIEWING → COMPLETED
    └──────────┴──────────────┴─────────────────┴─────────────┴──▶ FAILED / CANCELLED
```

SSE 注意：事件体 JSON 包装（避免换行/前导空格丢失）、反向代理关闭缓冲、心跳保活、客户端断开时级联取消 LLM 调用。

## 8.1 前端 UI/UX 标准

- 风格主流、高级、优雅；必须有动效（motion 库）：路由切换、列表进出场、骨架屏、状态切换、Agent 步骤流转；时长和缓动克制统一，尊重 `prefers-reduced-motion`
- **严禁一整页平铺**：用标签页、分步向导、抽屉/侧滑面板、可折叠分区、主从布局组织信息，每屏只聚焦一件事
- 统一设计令牌（颜色/圆角/阴影/间距），支持暗色模式；空状态、加载、错误状态都要设计
- 每个涉及 web 的 change 都要有 UI/UX 设计小节和截图验收

## 10. 论文实验设计

篇章级消融：

| 组别 | 配置 |
|---|---|
| D0 | 逐段独立翻译 |
| D1 | + 前块上下文（滑动窗口） |
| D2 | + 全文摘要 |
| D3 | + 预抽取并确认的术语表 |
| D4 | + 评审修正循环 |
| D5 | D4 并行策略（质量 vs 速度） |

指标：chrF（sacrebleu）、LLM 评审分（GEMBA-MQM 风格）、术语一致率、专名一致率、总耗时、token 成本。
测试集：开源项目官方中英文档（Vue / React / Kubernetes 等）5–10 篇 + FLORES-200 子集。
附加实验：语种识别器短文本准确率对比（lingua / fastText / LLM）。
⑦ 附加实验：E4 同传（识别错误率、语音翻译 chrF、分段延迟，级联 vs 百炼 S2S）、E5 图片翻译（OCR 准确率、块召回、术语，两步法 vs 单次视觉翻译）。
性能测试：Spring/Python 吞吐压测时 **mock LLM**；真实 LLM 延迟单独报告。

## 11. 风险清单

| 风险 | 应对 |
|---|---|
| 答辩被质疑"只是套壳" | 消融实验 + 轨迹可视化 |
| 反思循环 token 成本翻倍 | 快速路径、评审阈值、最多 2 轮 |
| 两跳 SSE 的缓冲/换行/断连 | JSON 包装事件、关闭代理缓冲、心跳、级联取消 |
| 双服务访问同库 | schema 级写权限划分，Python 只读 biz |
| 领域不匹配的 TM 拖累质量 | 相似度阈值过滤 |
| 范围膨胀 | 严格按第 7 节分层，① ② ③ 优先 |
| 实时语音链路延迟与稳定性 | ⑧.3：音频分段即时下发 + 前端 MediaSource 渐进播放（不支持时按段降级）；译文 / 回复边生成边切段合成、2 路预取；字幕不阻塞语音；句末识别让路；可选“极速”档；AI 对话可选端到端实时语音模型；剩余耗时（模型首字、Edge 首包）属网络与供应商因素，必要时选 S2S 引擎；WS 断线重连与优雅收尾 |
| 提示词效果随模型变化、改动后难以评估 | ⑧.4：提示词集中管理、带版本号并有快照测试；离线回归评测（同传 44 条、字幕 10 条、对话 6 段，LLM 评审）每次改动前后对比；处理示例不得与评测集重合，避免分数虚高；换模型时先跑评测再上线。仍未解决的难例（中文"他/她"代词、改口后的被否定内容、同音词纠错）依赖模型能力，已在报告中注明 |
| 断句只看静音：思考停顿把一句话切碎、AI 抢答、空白气泡 | ⑧.5：两段式断句与续说合并、语气词撤回、回复让位、择机开播、前端渲染规则；E6 用合成语音量化（文本规则零延迟代价；Smart Turn 在合成语音上未达缺省开启标准，改为可选）。合成语音与真人停顿语调不同，结论需真人语音复核；以名词或动词结尾的半句（如“请问…”）文本规则判断不了 |
| 免费 TTS（edge-tts）被限流 | 非致命降级到浏览器朗读；可配置 OpenAI 兼容 TTS；⑧.3 进程级 Edge 并发上限（缺省 4）与朗读缓存（含语速） |
